# Hybrid Execution: Automated Rule Extraction from LLM Logprobs

## The Problem

When an LLM processes a structured input (an incident report, a deployment request, an invoice), it does two fundamentally different kinds of work:

1. **Extraction** -- copying values that already exist in the input (incident IDs, names, dates, configuration values)
2. **Reasoning** -- synthesizing new information from the input (severity classification, root cause analysis, recommendations)

A pure-LLM approach treats both the same. The model spends tokens reproducing text it could have copied, and occasionally drops or transforms fields that should have been preserved verbatim. This wastes compute, adds latency, and introduces a class of errors that has nothing to do with reasoning quality.

The hybrid approach splits these concerns: deterministic rules handle extraction, the LLM handles reasoning. The key insight is that **the rules don't need to be written by hand** -- they can be automatically generated by analyzing the LLM's own output probabilities.

## The Automated Pipeline

The full pipeline runs in three commands. No human writes regex.

### Step 1: Probe -- Get Token Probabilities

The probe runs the LLM once with logprobs enabled (via Ollama's OpenAI-compatible API) and records the probability distribution over alternatives for every token in the output:

```
$ drift probe experiments/baseline-incident-triage.yaml -o probe.json

Tokens: 1204
Mean entropy: 0.208 bits
Deterministic (<0.1): 56%
High entropy (>0.5): 22%
```

Each token gets a Shannon entropy score. Entropy = 0 means the model was 100% certain of that token. Entropy > 0.5 means it was choosing between alternatives -- it was *reasoning*, not copying.

```
  Token probabilities for "Cascade Manufacturing Ltd."
  ─────────────────────────────────────────────────────
  "Cascade"          p=0.99  entropy=0.01   ◀── deterministic (copying from input)
  " Manufacturing"   p=0.98  entropy=0.02   ◀── deterministic
  " Ltd"             p=0.97  entropy=0.03   ◀── deterministic
  "."                p=0.99  entropy=0.01   ◀── deterministic

  Token probabilities for "P1"
  ─────────────────────────────────────────────────────
  "P"                p=0.72  entropy=0.89   ◀── high entropy (reasoning: P1 vs P2?)
  "1"                p=0.85  entropy=0.52   ◀── model is deciding, not copying
```

### Step 2: Synthesize -- Auto-Generate Rules

The synthesizer takes the probe data and the original input, and for each field in the LLM output:

1. **Computes field-level entropy** by averaging token entropies across the field's value
2. **Classifies the field**: below threshold = rule candidate, above = LLM required
3. **Traces the value back to the input text** to find where it came from
4. **Analyzes surrounding context** (labels, delimiters) to generate a regex
5. **Validates the generated regex** against the input to confirm it extracts correctly

```
$ drift synthesize probe.json --input tasks/incident_triage/input.md -o hybrid.yaml

AUTOMATED RULE SYNTHESIS
======================================================================
  Total fields analyzed:    27
  Rule candidates:          18 (entropy < threshold)
  Rules generated:          17
  Rules validated:          17
  LLM required:             10
  Automation rate:          63%
```

The auto-generation works by examining the context around each value in the input:

```
  Input text:                  "Account:     Cascade Manufacturing Ltd. (ACCT-4827)"
                                ^^^^^^^^     ^^^^^^^^^^^^^^^^^^^^^^^^^^^
                                label        value

  The synthesizer sees:
    - label "Account" followed by ":"
    - value "Cascade Manufacturing Ltd."
    - terminated by " ("

  Generated regex:              Account:\s*(.+?)\s*\(
  Validated:                    OK -- extracts "Cascade Manufacturing Ltd."
```

For values NOT found in the input (timestamps the model reformatted, severity it classified), the synthesizer checks if entropy is near-zero. If so, it's a `literal` -- the model always produces the same value, so we can hardcode it.

```
  LLM output field:            classification.severity = "P1"
  Token entropy:               0.018 (near-zero)
  Found in input:              No (model classified this)
  Rule type:                   literal (value: "P1")

  LLM output field:            root_cause_analysis.cause = "Buffer pool exhaustion..."
  Token entropy:               1.164 (high)
  Rule type:                   llm_required
```

### Step 3: Run Hybrid

The generated `hybrid.yaml` is used directly:

```
$ drift run experiments/auto-hybrid-incident-triage.yaml --runs 10

  Run 1/10... rules=17/17 43491ms
  Run 2/10... rules=17/17 23596ms
  ...
```

```
         │                                                       │

                       ┌────────────────────┐
                       │   PHASE 3: Merge   │

```

### Rule Types

| Type | Behavior | Auto-generated when |
|------|----------|-------------------|
| `regex` | Extracts first match, capture group 1 | Value found in input with identifiable label/context |
| `regex_all` | All matches as a list | Multiple instances of a pattern |
| `literal` | Fixed value, always emitted | Near-zero entropy but value NOT in input (model always says this) |

### Output Modes

| Mode | Behavior | Use when |
|------|----------|----------|
| `merge` | Rules and LLM each produce partial JSON, deep-merged | Output is structured data (JSON) |
| `llm_passthrough` | Rules parameterize the prompt, LLM output is final | Output is generated content (YAML, code) |

### What the comparison reveals

The auto-hybrid matches the baseline's functional quality while being 52% faster -- and requires zero human effort. But it can't beat the baseline because **it can only generate rules for fields the model already outputs**. The two failing tests (`incident_id`, `identifies_batch_risk`) fail because the model omits those fields entirely, so the auto-generator never sees them.

The manual hybrid achieves 100% by including a hand-written rule for `incident_id` -- a field the human knows should be there even though the model doesn't produce it. This is the boundary between automation and human judgment.

## The Entropy Boundary

The synthesizer's key decision is the entropy threshold. Below it, a field becomes a rule. Above it, the field stays with the LLM.

```
  ┌─────────────────────────────────────────────────────────────────┐
  │              Token Entropy Spectrum                              │
  │                                                                 │
  │  0.0          0.1          0.3          0.5          1.0  bits  │
  │  ├────────────┼────────────┼────────────┼────────────┤         │
  │  │                         │                         │         │
  │  │◀──── AUTO RULE ────────▶│◀────── LLM REQUIRED ──▶│         │
  │  │                         │                         │         │
  │  │ account_name    0.000   │ category        0.340   │         │
  │  │ reporter.name   0.015   │ cause           1.164   │         │
  │  │ tier            0.026   │ reasoning       1.008   │         │
  │  │ product         0.043   │ actions[0]      0.525   │         │
  │  │ environment     0.124   │ actions[1]      1.216   │         │
  │  │ severity (P1)   0.018   │                         │         │
  │  └────────────────────────┴─────────────────────────┘         │
  │                                                                 │
  │  Default threshold: 0.3 (configurable via --threshold)         │
  └─────────────────────────────────────────────────────────────────┘
```

Fields like `severity = "P1"` have near-zero entropy even though they require judgment -- the model is just very confident about this particular case. The auto-synthesizer captures these as `literal` rules, which is correct for this input but wouldn't generalize to other incidents. This is a tradeoff: the auto-generated rules are **input-specific** optimizations, not general-purpose extractors.

## Usage

### Full automated pipeline

```bash
# 1. Run baseline to get probe data
drift probe experiments/baseline-incident-triage.yaml -o probe.json

# 2. Auto-generate rules from probe + input
drift synthesize probe.json \
  --input tasks/incident_triage/input.md \
  -o tasks/incident_triage/hybrid_auto.yaml

# 3. Create experiment config referencing the auto-generated spec
# 4. Run hybrid experiment
drift run experiments/auto-hybrid-incident-triage.yaml --runs 10

# 5. Measure and compare
drift compare results/baseline/... results/auto-hybrid/...
```

### Tuning the entropy threshold

```bash
# More aggressive: capture more fields as rules (risk: may capture reasoning fields)
drift synthesize probe.json --input input.md --threshold 0.5

# More conservative: only capture very deterministic fields
drift synthesize probe.json --input input.md --threshold 0.1
```

## Security Considerations

The hybrid approach changes the security profile compared to pure-LLM execution.

### Prompt Injection

```
  Pure LLM:
  ┌──────────────────────────────────────────────────────────────┐
  │  Input (untrusted) ──────────────────▶ LLM ──▶ ALL fields   │
  │                                                              │
  │  Attack surface: every field in the output                   │
  │  A crafted input can influence any extracted or reasoned     │
  │  value in the output.                                        │
  └──────────────────────────────────────────────────────────────┘

  Hybrid:
  ┌──────────────────────────────────────────────────────────────┐
  │  Input (untrusted) ──┬──▶ Regex rules ──▶ 17 fields (safe)  │
  │                      │    (no LLM)                           │
  │                      │                                       │
  │                      └──▶ LLM ──────────▶ 2 fields (exposed)│
  │                                                              │
  │  Attack surface: only the 2 reasoning fields                 │
  │  Regex extraction is immune to prompt injection.             │
  └──────────────────────────────────────────────────────────────┘
```

The hybrid approach **reduces LLM exposure by 60%+**. Fields extracted by rules never touch the LLM, so prompt injection in the input text cannot affect those fields. Only the reasoning fields (classification, recommendations) remain vulnerable.

### Threat Model by Pipeline Stage

| Stage | Threat | Mitigation |
|-------|--------|------------|
| **Probe** (step 1) | Poisoned input corrupts logprob analysis, producing bad rules | Rule validation catches patterns that don't extract correctly; run probe on known-good inputs |
| **Synthesize** (step 2) | Rules derived from poisoned probe data | `_validate_pattern` rejects rules that fail extraction; manual review of generated `hybrid.yaml` |
| **Run** (step 3, rules) | None — regex is deterministic | N/A |
| **Run** (step 3, LLM) | Input injection alters reasoning output | Output schema validation; guardian LLM screening (adds latency) |

### Practical Notes

- **For offline analysis** (incident triage, data extraction): input is historical operational data, injection risk is low
- **For real-time pipelines**: consider input sanitization or a lightweight guardian model before the LLM step
- **Rule-extracted fields are tamper-proof**: even if the LLM is compromised, the 17+ regex-extracted fields are correct
- **JSON schema validation** on LLM output constrains what the model can produce, limiting injection impact

## Limitations and Future Work

**Tabular data**: The auto-generator struggles with invoice line items and grid data. Short values (quantities, prices) match multiple places in the input, causing regex to anchor on wrong positions. Tabular extraction needs a different strategy (column-aware parsing, not regex).

**Non-JSON output**: The synthesizer only works when the LLM produces JSON. For YAML/code generation tasks, the `llm_passthrough` mode with hand-written rules is currently the only option.

**Input-specific literals**: Fields marked as `literal` (like `severity = "P1"`) are correct for this specific input but won't generalize. A production system would need to run synthesis across multiple inputs and only keep patterns that are stable.

**Missing fields**: The auto-generator can only create rules for fields present in the LLM output. If the model omits important information, a human must add those rules manually.
